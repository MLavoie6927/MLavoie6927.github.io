01 / Security outcomes

Choose the primitive by the property you need.

Cryptography is not a single control. Confidentiality, integrity, authenticity, and non-repudiation require different constructions and different key-management decisions.

CONF / 01

Confidentiality

Encryption limits readable plaintext to entities that possess the correct decryption capability.

INTG / 02

Integrity

Hashes, MACs, and signatures expose unauthorized modification—but only MACs and signatures authenticate an origin.

AUTH / 03

Authenticity

HMAC proves possession of a shared secret. A digital signature verifies control of a private key.

AGIL / 04

Crypto-agility

Inventory, version, rotate, and replace algorithms or keys without redesigning the entire application.

Lab 01 · Integrity

SHA-256 digest

Observe the avalanche effect: a one-character change creates a substantially different 256-bit digest.

Security boundary: SHA-256 can confirm that bytes match a known digest. It does not prove who created the data, and it should not be used alone to store passwords.

Lab 02 · Confidentiality + integrity

AES-256-GCM vault

Derive a key from a passphrase, generate a fresh salt and IV, then produce authenticated ciphertext.

Production boundary: Passphrase-derived encryption is appropriate only for specific threat models. Production systems should normally use managed, randomly generated keys and defined rotation, backup, and revocation procedures.

Lab 03 · Message authenticity

HMAC sign + verify

Create a keyed authentication code, then demonstrate that a changed message or incorrect key fails verification.

Operational boundary: HMAC establishes shared-secret authenticity, not non-repudiation. Secret distribution, rotation, and constant-time verification belong in the system design.

Lab 04 · Public-key encryption

Ephemeral RSA-OAEP

Generate a temporary key pair, encrypt a short message with the public key, and decrypt it with the private key.

No key exists until you generate one. It remains only in memory.

Architecture boundary: RSA-OAEP encrypts only small values. Real applications use envelope encryption: a public-key mechanism protects a random symmetric data key, and AES-GCM protects the payload.

04 / System design

The hard part is the lifecycle, not the cipher.

Strong primitives still fail when keys are exposed, nonces repeat, trust anchors are replaced, plaintext leaks into logs, or recovery procedures are undefined.

Key lifecycle control points

The primitive is only one part of the design. Every key needs an owner, purpose, state, evidence trail, and tested failure path.

  1. 01
    GenerateApproved CSPRNG, algorithm and size policy, key purpose, and ownership.
  2. 02
    ProtectKMS or HSM boundary, least-privilege authorization, separation of duties, and backup decisions.
  3. 03
    UseNonce uniqueness, context binding, audit events, rate limits, and plaintext handling.
  4. 04
    RotateVersioned envelopes, staged re-encryption, compatibility testing, and rollback.
  5. 05
    Revoke and destroyIncident triggers, cryptographic erasure, retention requirements, and verification evidence.

What cryptography does not fix

Encryption reduces specific risks; it does not erase the rest of the attack surface.

  • !Compromised endpoints reading data after legitimate decryption
  • !Authorization mistakes granting the wrong principal access
  • !Secrets committed to source control, logs, images, or backups
  • !Weak randomness, nonce reuse, or silent algorithm downgrade
  • !Unavailable keys without tested recovery and escrow decisions

05 / 2026 crypto-agility

Plan the post-quantum transition now.

Quantum readiness starts with discovery: locate public-key dependencies, estimate confidentiality lifetimes, identify vendor roadmaps, and design controlled hybrid migrations.

NIST FIPS 203

ML-KEM

A module-lattice key-encapsulation mechanism for establishing shared secrets, standardized with three parameter sets. Implementers should also review NIST's published errata.
