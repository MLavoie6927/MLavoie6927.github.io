02 / Architecture

Three systems, one reviewable decision

01 / Intune

Target and evaluate

A named 20-user pilot group and corporate Windows assignment filter narrow the compliance policy. BitLocker, Secure Boot, OS level and a fresh cloud evaluation form the pilot gate.

The Intune filter does not target Conditional Access.

02 / Entra

Decide access

A separate Conditional Access policy targets the pilot users and selected Microsoft 365 resources, requires a compliant device, excludes documented emergency access, and starts in Report-only.

Report-only predicts impact; it does not block.

03 / Sentinel

Correlate and escalate

Entra sign-in and audit data can support Sentinel investigation. Intune audit and operational exports add change and device context. A fresh per-device compliance verdict still needs the authoritative Intune report or Graph check.

No claim of a live connector or deployed analytic.

Population boundary

1,800 corporate Windows endpoints are eligible for this staged change. The 350 personal phones, 150 kiosks and 100 shared Windows stations require separate analysis. A user-based pilot can still affect sign-ins from another device, so the test plan checks cross-device behavior.

Investigation order

  1. Match group object IDs, assignment target and filter preview to the signed roster.
  2. Check per-setting compliance and device last sync; isolate Not evaluated from truly noncompliant.
  3. Match user, device ID, resource, time and applied Conditional Access policy on the exact sign-in.
  4. Check change audit, approver and support ticket before attributing a failure.

Stop conditions

  • Any unapproved user or device in scope.
  • Any pilot device without a fresh evaluated result.
  • A sign-in outcome that contradicts the planned grant.
  • An admin can perform an out-of-scope edit or destructive action.

The fictional pilot hits the second condition. Ring 2 stays on hold.

04 / Sentinel handoff

Alert on access anomalies; verify the cause

This is a detection design, not a claim of a running rule. It prioritizes a targeted sign-in outcome alongside audit change context and an independently checked Intune state.

Candidate signal

For pilot identities, review failed or report-only Conditional Access outcomes for the exact pilot policy and resource. Correlate with recent policy or group changes. Enrich with Intune device status from a permitted, fresh source before declaring a compliance failure.

A sign-in denial alone does not identify which policy caused it.

False positives and blind spots

  • Other Conditional Access policies can cause the access failure.
  • Report-only results are not actual blocked access.
  • New enrollment, stale sync and unsupported hardware can look similar from a single signal.
  • Intune exports have different timing by category; an absent row is not a passing device.

05 / Endpoint telemetry

Defender and Sysmon add context, not a compliance verdict

Marc’s Sentinel, Defender for Endpoint and Sysmon playbook extends this case beyond the sign-in. These sources help test whether the stale laptop is otherwise healthy and whether the access anomaly is part of broader endpoint activity.

DEFENDER FOR ENDPOINT

Sensor and device timeline

Verify onboarding, sensor health, last seen and a controlled test event. Pivot from a suspicious process tree to device network activity and the Defender XDR incident. A healthy sensor does not prove Intune compliance or AMA collection.

WINDOWS EVENTS + AMA

Source to workspace

On eligible Azure or Arc hosts, verify AMA health, DCR association and selected Windows Security events in SecurityEvent. A missing row can mean the source did not generate the event, the DCR excluded it, or ingestion is delayed.

SYSMON + AMA

Process detail

Validate a tuned Sysmon configuration locally, then check the Sysmon operational channel through a tested DCR path into WindowsEvent. Join with Defender using device, user and time; do not rely on a reused PID alone.

Correlation rule: Do not collapse these signals into one health score. Intune compliance is evaluated in Intune; Conditional Access is observed on the exact Entra sign-in; Defender, Windows and Sysmon supply separate endpoint evidence. Sentinel can help investigate where those streams are actually connected and populated.

SOC incident-assist path

  1. Start with the sign-in and applied Conditional Access policy ID.
  2. Check the Intune device ID and current cloud evaluation.
  3. Pivot to Defender device timeline, sensor status and any related process or network alert.
  4. Inspect SecurityEvent and WindowsEvent only if the pilot has confirmed AMA/DCR coverage.
  5. Hand the case to a human analyst with source links, time range, missing data and owner.

Automation boundary

A Sentinel Logic App playbook may enrich an incident, add tasks and notify the team after its trigger, permissions and run history are validated. The tabletop does not automatically isolate a device, disable an account or wipe it. Any disruptive action needs a named approval and rollback path.

06 / Senior engineer handoff

Hold, repair, retest, approve

Endpoint lead

Own the stale endpoint investigation. Verify enrollment, ownership, assignment, local security state, last sync and fresh per-setting result. Do not widen the ring while it is Not evaluated.

Identity + SOC

Review exact sign-ins and applied Conditional Access policies, monitor support tickets, and separate expected test denials from user impact. Keep the new CA policy in Report-only until promotion gates pass.

Independent approver

Compare the corrected 20-device roster, reports, sign-ins, negative RBAC tests and repair route. Record an explicit decision before the +80 wave.
