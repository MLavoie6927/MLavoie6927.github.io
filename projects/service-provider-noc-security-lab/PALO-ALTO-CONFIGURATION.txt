IMPORTANT BOUNDARY
==================
This is a public-safe candidate configuration for an isolated PAN-OS lab VM.
PAN-OS object paths and supported flood settings can vary by release, license,
and management plane. Review the candidate diff, validate each command on the
authorized target release, and use formal change control before commit.

No credentials, API keys, certificates, production thresholds, serial numbers,
or organization-specific identifiers belong in this file.

POLICY INTENT
=============
1. Permit public HTTP/HTTPS only to PUBLIC-WEB-VIP 198.51.100.50.
2. Permit authoritative UDP/TCP DNS only to PUBLIC-DNS-VIP 198.51.100.53.
3. Deny unsolicited IPv4 ICMP from untrust to public services.
4. Deny all unmatched untrust traffic.
5. Log at session start and end for permitted public services.
6. Attach threat-prevention and file-analysis profiles where licensed.
7. Apply zone and classified DoS protection with lab baseline thresholds.
8. Preserve internal troubleshooting from an authorized management zone.
9. Escalate upstream when attack volume saturates the external circuit.

BOUNDED LAB TRAFFIC VALIDATION
==============================
Do not use unrestricted flood flags. Generate only a small, bounded sample
against the isolated documentation VIP. Example from a lab traffic host:

nping --tcp -p 443 --flags syn --rate 100 --count 1000 198.51.100.50

Guardrails:
- Destination must resolve only inside the isolated lab.
- Maximum rate in this runbook is 100 packets/second.
- Maximum count is 1,000 packets.
- Confirm the target is owned and the test window is approved.
- Stop immediately if traffic leaves the lab or affects unrelated services.

For high-rate dashboard examples, use sample_telemetry.json. Those values are
synthetic and do not require generating 12,844 SYN packets per second.


ROLLBACK
========
Rollback trigger examples:
- Public web or DNS validation fails after the approved change window begins.
- Unexpected rule match, route loss, session exhaustion, or management loss.
- Logging pipeline failure removes required visibility.
- Customer impact exceeds the approved scope.

Rollback process:
1. Use out-of-band access.
2. Load the pre-change named configuration snapshot.
3. Review the diff to ensure only the intended candidate changes are removed.
4. Commit the rollback.
5. Re-run routing, NAT, security-policy, service, and SIEM validation.
6. Preserve before/after evidence and open a problem record.

Do not use a blind rollback if unrelated changes were committed after the
snapshot. In that case create a targeted candidate rollback under change control.


ENGINEERING CONCLUSIONS
=======================
- A port allowlist is not DDoS protection; allowed applications can be flooded.
- Zone protection protects the firewall zone; classified DoS policy protects
  selected services and sources/destinations.
- A firewall behind a saturated circuit cannot recover consumed upstream capacity.
- Upstream scrubbing, provider ACLs, BGP FlowSpec, or RTBH must be pre-authorized.
- Denying untrusted IPv4 ICMP is scoped here to public-service ingress. Internal
  diagnostics remain available from an authorized management zone.
- Thresholds are engineering values derived from baselines, capacity, and risk,
  not numbers copied unchanged from a portfolio project.
